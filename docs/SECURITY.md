## 1. 威胁模型

### 1.1 设防对象

| # | 威胁 | 影响 | 对策 |
|---|---|---|---|
| T1 | 云数据库被拖库 / 内部人员读数据 | 凭据、证件图、手机号泄露 | 客户端加密，云端只存密文 |
| T2 | 云存储文件被直接枚举下载 | 证件照片泄露 | 文件内容加密 + fileID 不可猜测 |
| T3 | 抓包 / 中间人 | 传输泄露 | HTTPS + 应用层加密，服务端不见明文 |
| T4 | 手机丢失，他人打开微信进入小程序 | 全部资料可见 | 保险箱独立主密码 + 自动锁 |
| T5 | 暴力破解主密码 | 离线爆破 | KDF 高迭代 + 服务端失败退避 |
| T6 | 越权访问他人数据 | 横向越权 | 云函数 `owner_openid` 强绑定 + 前端零直连 |
| T7 | 日志泄露 | 明文进日志 | 白名单脱敏，只记字段名与长度 |
| T8 | 客户端被篡改 / 注入 | — | 不在范围内（小程序沙箱由微信保证） |

### 1.2 明确不设防（能力外）

| 不设防 | 原因 |
|---|---|
| 微信官方能读取本地存储 | 小程序沙箱内，微信有一切权限；不用"端到端加密"表述 |
| 已 root / 越狱设备上的内存抓取 | 超出小程序可控范围 |
| 用户自己把恢复码拍照发群里 | 社工，非技术问题 |
| 服务端主动下发恶意代码 | 信任微信云开发平台本身 |

## 2. 密钥体系

### 2.1 层次

```
主密码（用户记忆，仅存在于输入框）
   │  KDF（PBKDF2-HMAC-SHA512，600,000 迭代，salt 32B 随机）
   ▼
KEK_pwd ──┐
          ├── 包裹 ──► MK (32B, CSPRNG 生成，永不离开客户端内存)
恢复码（32B 随机，Base32 展示）│
   │  KDF（同上，独立 salt）   │
   ▼                          │
KEK_rec ──────────────────────┘

MK ──AES-256-GCM──► 每条 secure_item.payload_enc（唯一 12B nonce）
MK ──AES-256-GCM──► 每个敏感字段 values[k].ct（唯一 12B nonce）
MK ──AES-256-GCM──► 每个证件/附件文件内容（分块，每块唯一 nonce）
```

| 名称 | 长度 | 生成 | 存储位置 | 生命周期 |
|---|---|---|---|---|
| 主密码 | ≥ 10 字符 | 用户输入 | **不存** | 仅解锁瞬间存在于输入框 |
| `salt` | 32B | `crypto.getRandomValues` | `vaults.kdf_params.salt`（明文，安全） | 永久 |
| `KEK_pwd` | 32B | KDF 输出 | **不存** | 解锁期间内存 |
| `MK` | 32B | CSPRNG | 云端只存两个包裹体 | 解锁期间内存 |
| 恢复码 | 32B | CSPRNG | 用户抄写 | 永久 |
| `KEK_rec` | 32B | KDF(恢复码) | **不存** | 恢复时临时 |
| 数据 nonce | 12B | CSPRNG，**每次加密重新生成** | 随密文一起存 | 与密文同寿命 |

### 2.2 为什么不用主密码直接加密数据

若 `MK = KDF(主密码)`，改密码 = 重新加密全部数据。分离出 MK 后，改密码只需用新 KEK 重新包裹 MK，数据不动。这是必须的，否则"改主密码"在 1000 条数据时会超时失败。

### 2.3 密钥信封（Key Envelope）

所有敏感值统一存为：

```ts
interface Envelope {
  __enc: 1;      // 哨兵，防止明文误当密文解析
  ct: string;    // Base64 密文（含 GCM tag）
  iv: string;    // Base64，12 字节
  kv: number;    // key_version
}
```

**AAD（附加认证数据）**：`utf8(`${userId}:${itemId}:${fieldKey}:v${kv}`)`

作用：把密文绑定到"哪个用户的哪条记录的哪个字段"。攻击者若把 A 用户的密文复制到 B 用户的记录里，GCM 校验失败 → 解密报错而非返回错误数据。

字段值的明文载荷是 `{"v":1,"value":<原值>}`（`utils/crypto/fields.ts`），不是裸字符串：数字 / 开关 / 多选在往返中不会退化成字符串，载荷版本也可单独演进。

**记录 `_id` 由客户端预生成**：AAD 需要 `itemId`，若先写库再回填密文，中间会有一段明文窗口，失败还会留下半条记录。因此 `record.create` 接受 `clientId`（32 位 hex），校验未被占用后直接以该 ID 写入。

### 2.4 唯一 nonce 保证

- 每个 nonce 由 `crypto.getRandomValues(new Uint8Array(12))` 生成。
- 12 字节随机 nonce 下，同一密钥加密 2³² 次碰撞概率约 2⁻³³，对本产品（单用户 ≤ 10⁴ 条）足够。
- **禁止**用计数器、时间戳、固定值作 nonce。
- 单元测试强制：连续加密同一明文 1000 次，nonce 全不相同。

### 2.5 密钥版本与轮换

- `key_version` 从 1 开始，每次 `rotateKey` +1。
- 轮换流程：客户端用旧 MK 解出全部 → 生成新 MK → 逐条重加密（写入 `rewrapped` 数组）→ 云函数事务内批量更新 → `key_version` +1。
- 轮换是**分批**的（每批 20 条），中断可续（未重加密的条目 `kv` 仍是旧值，解密时按 `kv` 选择正确 MK）。
- 因此客户端需同时持有 `MK[1..n]` 中仍在使用的版本，仅在新版本全量完成后丢弃旧 MK。

### 2.6 主密码丢失恢复

`vaults.recovery_wrap` = `AES-256-GCM(KEK_rec, MK)`。

- 恢复码 32 字节 → Base32（52 字符，去掉易混字符 `0/O/1/I`），按 `XXXX-XXXX-...` 分组展示。
- 恢复流程：输入恢复码 → 派生 `KEK_rec` → 解出 MK → 用新主密码派生新 `KEK_pwd` → 重写 `verifier` → 记录 `security_logs.action='recover'`。
- **风险明示（必须出现在 UI 上）**：恢复码等同于主密码。任何拿到恢复码的人可完整解密保险箱。**不存云端、不存本地、不上传截图**。

### 2.7 为什么没有第三条恢复路径

零知识前提下，能解开 MK 的路径只有两条：主密码、恢复码。若再引入"客服重置"或"安全问题"，就必须有一个持有密钥的第三方——那就不再是零知识。**本产品选择宁可丢数据也不留后门。** 该取舍在首次初始化时以二次确认弹窗明确告知。

### 2.8 放弃式重置（reset）

当「主密码 + 恢复码」双双丢失时，提供唯一的兜底：`vault.reset` 删除云端 vault 记录，回到未初始化状态。这是"丢数据"而非"找回"——重置后所有 `encrypted=1` 的附件因 MK 丢失而永久无法解密（服务端无 MK，无法代解）。触发前以二次确认弹窗明示，并写 `security_logs.action='reset'` 留痕。

## 3. 加密范围（逐字段决定）

| 数据 | 加密 | 可搜索 | 理由 |
|---|---|---|---|
| 资料标题 `title` | ❌ | ✅ | 标题泄露的信息量低于失去搜索的代价 |
| 资料摘要 `summary` | ❌ | ✅ | 同上 |
| 普通字段值 | ❌ | ✅ | 无敏感性 |
| **手机号** | ✅ | ❌ | 高敏感，可定位到人 |
| **证件号码** | ✅ | ❌ | 高敏感 |
| **保险箱全部内容** | ✅（整条） | ❌ | 最高敏感 |
| **附件文件名** | ✅ | ❌ | 文件名常含"身份证正面.jpg"这类信息 |
| **附件内容** | ✅ | — | 证件图片本质是身份凭证 |
| 人物姓名 | ❌ | ✅ | 关系网核心索引 |
| 人物头像 | ❌ | — | 头像公开度高；加密会导致列表页无法显示（体验不可接受），此取舍明示于 §3.1 |
| 纪念日标题/日期 | ❌ | ✅ | 敏感度低 |
| 分类名 / 标签名 | ❌ | ✅ | 用户自定义，通常不含隐私 |
| 搜索历史 | ❌ | ✅ | **仅存本地**，不上云 |

### 3.1 头像与封面为什么不加密

列表页/首页头像需要**批量展示**。若加密，每屏 20 个头像要下载 20 个密文并逐个解密，首屏延迟与流量不可接受，且解密需 MK 常驻内存（扩大暴露窗口）。

**取舍**：头像不加密，但上传时强制 canvas 重编码剥离 EXIF（GPS 等）并等比缩放到 ≤512（`utils/image.ts` 的 `stripExif`，显示时 `aspectFill` 方形裁剪）。用户若上传含敏感信息的照片作为头像，属自发行为，UI 在头像选择处提示"头像不加密，请勿使用证件照"。

### 3.2 实施状态（随阶段更新，不提前宣称）

| 能力 | 状态 | 说明 |
|---|---|---|
| 敏感字段不进 `search_text` / `summary` | ✅ 已实现（P2） | `normalize.js` 的 `flattenValues` 跳过 `sensitive` 字段与信封对象 |
| 敏感字段详情页掩码 | ✅ 已实现（P2） | `maskValue`，需用户主动点「显示」才渲染原值 |
| 敏感字段落库加密 | ✅ 已实现（P5） | 保存时把 `sensitive` 字段值封成信封（AAD 绑定 `userId:recordId:fieldKey`）；新建前预生成 `_id` 保证首次写入就绑对。判定按值的形态（`__enc=1`），不看模板 `encrypted` 标志，兼容存量明文 |
| 存量明文回填 | ✅ 已实现（P5） | 设置页「回填历史明文」：`record.backfillBatch` 按 `_id` 升序扫描 → 客户端判断哪些敏感字段仍是明文 → 封包后 `record.update` 写回。幂等（信封跳过），可中断重跑；模板已删的记录跳过不猜 |
| 附件内容加密 | ✅ 已实现（P3） | `utils/crypto/`（KDF / AES-GCM / 信封 / 文件密文）+ `keystore`（主密码/恢复码/MK 信封）+ `vault` 云函数（init/status/changePassword/recover/reset/audit）+ `file-uploader` 端到端接入（加密上传 / 解密预览）。加密附件在云存储为密文（`*.enc`），元数据里 `encrypted=1` 并携带 `enc_meta={alg,kv,ctx}`；文件名加密为 `name_enc` 信封 |
| 保险箱整条加密 | ❌ 未实现（P5） | |
| 头像 EXIF 剥离 + 缩放 | ✅ 已实现（P3） | `utils/image.ts` 的 `stripExif`：canvas 重编码剥离 GPS 等元数据 + 等比缩放 ≤512，用于明文头像上传 |

> **阶段五的迁移义务**：P5 接入 MK 后，需要对所有 `encrypted=false` 的敏感字段值做一次加密回填（读明文 → 写信封 → 置 `encrypted=true`）。在回填完成前，这些字段依然是明文。这条不是可选项，是 P5 的验收条件之一。

**因此现在的诚实表述是**：「新写入的敏感字段以密文存储，历史记录尚未回填」，而不是「所有敏感字段已加密」。模板编辑页与资料详情页都按这个口径写文案。

## 4. 文件加密流程

### 4.1 加密上传

```
1. wx.chooseMedia / chooseMessageFile
2. 校验：size ≤ 20MB，mime 白名单（image/*, application/pdf）
3. wx.getFileSystemManager().readFile({ filePath, encoding: undefined })  → ArrayBuffer
4. 取 12B 随机 nonce
5. AES-256-GCM(MK, nonce, plainBuf, aad=`${userId}:${fileId}:content:v${kv}`) → cipherBuf
6. 落临时文件 `*.enc`
7. wx.cloud.uploadFile({ cloudPath: `u/${userId}/${uuid}.enc`, filePath })
8. 调 attachment.confirmUpload 登记元数据
9. 删除临时文件
```

- 无流式加密能力（小程序无 `crypto.subtle`、无 TransformStream），必须全量读入内存。**20MB 上限由此而来**，不是随意定的。
- 加密后体积 = 明文 + 16B tag + 20B 头部，可预估进度。
- `sha256` 计算在明文阶段完成，用于去重与完整性校验。

### 4.2 解密预览

```
1. wx.cloud.downloadFile({ fileID }) → tempFilePath
2. readFile → 密文 ArrayBuffer
3. 按 enc_meta.iv / kv 解密 → 明文 ArrayBuffer
4. 写临时文件（扩展名按 mime 还原）
5. 图片 → wx.previewImage；PDF → wx.openDocument
6. 页面 onUnload 时删除临时文件
```

### 4.3 缩略图策略

- **不生成加密缩略图**。证件类附件的列表项只显示占位卡片（"已加密 · 点击解锁查看"），不泄露图像内容。
- 普通资料附件（非证件）可生成明文缩略图，但需用户在上传时勾选"生成缩略图"（默认关闭，仅图片类型）。默认关闭是因为缩略图=明文图像，等于绕过加密。

### 4.4 元数据隐私

| 元数据 | 处理 |
|---|---|
| 文件名 | 加密（`name_enc`），列表显示 `name_mask`（如"附件 1"） |
| 云存储路径 | `u/{userId}/{uuid}.enc`，不含原文件名、不含时间 |
| MIME | 明文（不足以泄露内容） |
| 尺寸 | 明文（弱标识） |
| EXIF | **上传前剥离**（用 canvas 重绘），避免 GPS 泄露 |

## 5. 解锁与锁定生命周期

```
锁定态 ──输入主密码──► 派生 KEK_pwd ──解密 pwd_wrap──► 得到 MK（GCM 失败即密码错）
   ▲                                              │
   │                                              ▼
   └──── onHide / 超时 / 手动 / 切换后台 ◄──── 解锁态（MK 在内存）
```

| 事件 | 行为 |
|---|---|
| 进入保险箱 | 若未初始化 → 引导初始化；已初始化 → 强制解锁 |
| `onHide` | **立即锁**（不只是超时）。因为切后台时截图会留存，且返回时不应免密 |
| 无操作超时 | 默认 120s，可配 30s～600s |
| 手动锁 | 立即清 MK 引用，跳回解锁页 |
| 解锁态离开 `vault` 路由栈 | 立即锁 |
| 连续失败 5 次 | 服务端锁定 5 分钟，此后指数退避至 60 分钟 |

### 5.1 「清除临时明文」的真实含义

```ts
// 实际做法
this.mk.fill(0);        // 对 Uint8Array 可行 —— 真的清零了
this.mk = null;
this.plainCache = null; // 对象引用置空，依赖 GC
```

- **`Uint8Array` / `ArrayBuffer` 可以真正清零**（`fill(0)`），因为它们是可变字节缓冲。
- **JS 字符串无法清零**。任何 `string` 类型的密码/明文在 GC 前都可能残留在堆内存中，且无法主动擦除。
- 因此设计上：**密码与明文尽可能以 `Uint8Array` 流转，只在必要的 UI 边界才转 `string`，且转完立即丢弃引用。**
- 诚实结论：能做到「缩短敏感数据在内存中的存活窗口」，**做不到「保证内存中无残留」**。

## 6. 平台侧安全

| 项 | 措施 |
|---|---|
| 数据库权限 | 15 个集合统一 `{"read": false, "write": false}`，前端零直连 |
| 鉴权 | 唯一可信来源 `cloud.getWXContext().OPENID`；payload 中的 `openid`/`user_id` 一律忽略并告警 |
| 归属校验 | 所有 `where` 第一项 `owner_openid`；单条读取后二次比对，不等即 403 |
| 构建黑名单 | `vault` 云函数为「加密附件」的密钥前置，不挂闸门；P5 的「密码保险箱」（secure_items CRUD）在 `SHILU_BUILD=public` 时返回 403（`assertFeatureAllowed('vault')` 由届时新增的 secure_items action 触发） |
| 参数校验 | 服务端白名单字段 + 类型 + 长度 + 枚举，禁止透传未知字段入库 |
| 输入净化 | 正则元字符转义；`search_text` 长度截断；禁止用户输入拼入 `db.RegExp` 未转义 |
| 越权测试 | 每个云函数必须有「用 A 的 openid 读 B 的 docId」用例，断言 403 |

## 7. 已知限制与诚实声明

### 7.1 未实现 Argon2id（强制披露）

- 需求要求 Argon2id。**本期未实现。**
- 原因链：小程序无 `crypto.subtle` → 只能走 WXWebAssembly → WXWebAssembly 仅接受**包内 `.wasm` 路径**（不接受 ArrayBuffer），基础库需 ≥ 2.13.0 → Emscripten 默认产出依赖 `wasi_snapshot_preview1` import → 小程序不支持该 import（社区实测报 `Import #0 module="wasi_snapshot_preview1" error`）→ 需定制 `STANDALONE_WASM` 编译 → **本机无微信开发者工具、无真机，无法验证**。
- 当前落地：**PBKDF2-HMAC-SHA512，600,000 迭代**（OWASP 2023 对 PBKDF2-SHA256 建议 600k，SHA512 同量级保守取值）。
- 缓解：KDF 可插拔。`vaults.kdf_algo` + `kdf_params` + `key_version` 已预留，Argon2id PoC 通过后按 §2.5 迁移，无需改数据结构。
- 未验证项：PBKDF2 600k 在低端安卓机的真实耗时（预期 1～4s，需实测后调参；参数变更同样走 `key_version`）。

### 7.2 不使用「端到端加密」表述

- 保险箱与加密附件属于**客户端加密**（client-side encryption）。
- 但小程序运行环境由微信控制，微信理论上可读取内存。因此**不满足严格意义的 E2E 定义**（E2E 要求通信双方之外无第三方可解密，而终端本身受平台控制）。
- 对外统一表述为「客户端加密，云端仅存密文」。

### 7.3 `unlock` 的服务端校验防不了什么

`verifier` 比对只能防止「本地输错密码」，**不能**防止服务端作恶（服务端可以直接返回成功或拒绝服务）。真正的安全性来自：MK 只在客户端派生、云端只有密文。服务端校验的价值是省掉一次无效的本地解密尝试。

### 7.4 其他

| 限制 | 说明 |
|---|---|
| 单文件 20MB 上限 | 无流式加密，需全量入内存 |
| 无生物识别 | 个人主体 SOTER 能力受限，本期不做 |
| 无内存级防护 | 见 §5.1 |
| 恢复码是单点 | 见 §2.6，泄露即全泄露 |
| 剪切板复制密码 | 复制后 30s 自动清空剪切板（`wx.setClipboardData` 后可覆写），但系统剪贴板历史仍可能留存，UI 提示 |

## 8. 日志脱敏规范

**白名单制**：只允许记录以下形态。

| 允许 | 禁止 |
|---|---|
| `field=password, len=20` | `password=abc123` |
